# Архитектурное решение по кешированию

## Мотивация
Какие проблемы решаем:
- Проблемы клиентов с низкой скоростью информирования о состоянии заказа
- Проблемы пользователей API - с той же проблемой
- Медленная работа списка заказов в MES UI

Складывается впечатление (которое стоит подкрепить метриками), что узкое место в хранилище MES. Оптимизация работы БД - обязательной шаг, но онт требует специалистов и времени.  Кеширование должно решить часть проблем, пока решается основная - оптимизация БД.

## Предлагаемое решение
Предлагается кешировать две системы: MES и MES UI.
Стандатное решение на базе Redis.

### MES
Кеширование MES должно помочь с первыми двумя проблемами, применим паттерн Write-Through.
[Диаграмма](sd-mes.puml)
**Обоснования выбора:**
- запись здесь чаще чем чтение
- не Write-Behind - т.к. потеря данных недопустима
- запись идет неявно для пользователя, поэтому некоторые задержки, которые неизбежно появятся при внедрении этого паттерна, будут незаметны для конечного пользователя

**Стратегия инвалидации**
Write-Through + TTL (Time to Live) с фоновым прогревом
Обоснование:
- Write-Through - консистентность и надежность. Любая операция обновления данных сначала попадает в кеш, а затем немедленно и синхронно применяется в MES Storage. Клиентское приложение получает подтверждение операции только после успешного выполнения и там, и там. Простота реализации: логика *записал в хранилище — обновил кеш* проста и надежна. Устойчивость к сбоям: если кеш полностью упадет, система продолжит работать, только медленнее.
- TTL - в данном случае - контроль за объемом памяти: не позволяет кешу бесконечно расти, вытесняя старые, невостребованные данные. Актуальность для чтения: устанавливая TTL (согласно метрикам производительности) находся баланс между производительностью и *устареванием* данных.

### MES UI
Для MES UI применим Cache-Aside.
[Диаграмма](sd-mes-ui.puml)
**Обоснования выбора:**
- только чтение, крайне редкое изменение - паттерны *write-* будут неэффективны
- Refresh-ahead нагрузит и без того нагруженную MES
- в отличие от Read-Through, Cache-Aside позволит делать более сложные запросы, не меняя постоянно модель в кеше
- есть шаблон использования - чаще всего это последние заказы - поэтому попадание в кеш ожидается высоким

**Стратегия инвалидации**
Комбинированная стратегия: TTL + явная инвалидация по событиям
Обоснование:
 - TTL. Срок жизни надо будет подобрать эмпирически. Список заказов - сущность, которая обновляется не очень быстро. Можно предположить (в соответствии с метриками) что задержка на несколько минут не будет критической. В реализации очень проста - большинство решений кеширования поддерживают TTL *из коробки*.
- Явная инвалидация по событиям. При любой операции записи, которая меняет данные в системе обновляем кеш.
