# Выбор и настройка мониторинга в системе

## Мотивация
Есть подозрения в неполадках отдельных частях системы. Чтобы не действовать наугад и терять время (и деньги) стоит сделать систему более наблюдаемой. Необходимо завести метрики, они покажут *состояние здоровья* отдельных компонентов системы, слабые места, которые надо будет исправить.
Это не разовая акция, вот плюсы дальнейшей работы: 
- можно будет наблюдать потенциальную деградацию под нагрузкой, заранее предотвращать сбои
- настроить предупреждения о вероятных сбоях еще до их возникновения, что может помочь сэкономить деньги на их восстановление и предупредить потерю репутации компании
- алертинг позволит заранее видеть слабые места, которые выявляются под нагрузкой (а мы же планируем расширяться) и исправлять возможные сбои еще до их возникновения
- атаки снаружи (и потеециальные внутренние утечки) быстрее разбираются на прозрачной системе

## Выбор подхода к мониторингу
- USE: анализ ресурсов (CPU, память, диски, сеть). Отвечает на вопрос "Ресурс перегружен?"
- RED: анализ сервисов (веб-сервисы, API, микросервисы). Отвечает на вопрос "Сервис работает хорошо для пользователей?"
- Четыре золотых сигнала (FGS): универсальные сигналы для любого сервиса. Отвечают на вопрос "Каково общее состояние сервиса?"

Постепенно нужно внедрять USE для каждого сервиса.
На базе полученных данных (и иных специфичесхих метрик) можно построить FGS - как наиболее универсального подхода к мониторингу сервисов.

FGS показывает *что* плохо, а USE помогает найти *почему* это плохо.

## План действий
### Выбор и развертывание стека мониторинга
**Задача:** Создать отказоустойчивый кластер для хранения временных рядов.
**Технология:** Prometheus, как основной сборщик и хранилище метрик.

**Задача:** Реализовать унифицированный интерфейс для дашбордов и визуализации.
**Технология:** Grafana.

**Задача:** Реализовать систему алертинга для уведомления инженеров.
**Технология:** Alertmanager (часть стека Prometheus) для управления алертами, группировки и маршрутизации уведомлений в нужные каналы (Slack, Telegram, Email).

### Интеграция мониторинга инфраструктуры
**Задача:** Внедрить сбор метрик USE для всех серверов (виртуальных машин, контейнеров).
**Решение:** Установить Node Exporter (Prometheus) на все серверы для сбора данных по CPU, памяти, дискам, сети.

### Интеграция мониторинга сервисов и приложений
**Задача:** Внедрить сбор метрик Four Golden Signals для каждого сервиса.
**Решение:** Реализовать endpoint /metrics в каждом сервисе в формате, понятном для Prometheus.
**Технология:** Использовать клиентские библиотеки Prometheus для имеющегося стека технологий.
**Подход:** В коде сервисов добавлять счетчики (errors, requests), гистограммы (latency, response size).

**Задача:** Настроить мониторинг качества внешних вызовов (к БД, кэшу, другим сервисам).
**Решение:** Инструментировать клиенты для внешних вызовов, добавляя метрики latency и error rate.

### Интеграция мониторинга сторонних компонентов (RabbitMQ, БД, Redis, S3)
**Задача:** Настроить сбор метрик для RabbitMQ.
**Решение:** Развернуть RabbitMQ Exporter, который будет собирать метрики из AMQP и предоставлять их Prometheus.

**Задача:** Настроить сбор метрик для базы данных PostgreSQL.
**Решение:** Развернуть Postgres Exporter.

**Задача:** Настроить сбор метрик для Redis.
**Решение:** Развернуть Redis Exporter.

**Задача:** Настроить сбор метрик для S3 хранилища.
**Решение:** В зависимости от реалиции S3 (докупить услугу облачного провайдера, подключить имеющийся функционал, наприсать свой).

### Создание дашбордов
**Задача:** Создать единый источник истины для состояния системы.
**Действие:** В Grafana создать дашборды:
- Инфраструктура: USE-метрики по всем серверам (CPU, Memory, Disk I/O, Network).
- Сервисы: FGS-метрики по каждому сервису.
- Бизнес-логика: Ключевые бизнес-показатели (посетители, конверсия, отказы).
- Очереди: Детальный дашборд по RabbitMQ (описаны ранее).
- Базы данных и кэш: (описаны ранее).
**Подход:** Хранить конфигурацию дашбордов в виде кода (JSON) в системе контроля версий (Git) для ведения истории изменений и быстрого развертывания.

### Настройка алертинга
**Задача:** Реализовать упреждающее оповещение о проблемах.
**Действие:** Описать правила алертинга в YAML-файлах (для Prometheus) и также хранить их в Git.
Приоритизация: реализовать как минимум два уровня серьезности:
- Warning: Предупреждение о потенциальной проблеме, требующей внимания (например, медленный рост дискового пространства БД).
- Critical: Критическая проблема, требующая немедленной реакции (например, диск заполнен на 95%, ошибки 5xx > 1%).
Настроить маршрутизацию в Alertmanager так, чтобы Critical алерты отправлялись в круглосуточный чат/на телефон, а Warning — только в рабочее время.
